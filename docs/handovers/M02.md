## Client behavior and integration limits

- OTP request returns a generic 202 even when suppressed; this does not prove an SMS was sent. Other development OTP codes are printed in the server terminal; the single fixed sign-in pair is listed below.
- Use one stable installation UUID as deviceId. New accounts need displayName; display-name-required allows retrying the same valid OTP with the name.
- OTP expires in 10 minutes; five failed attempts consume it. Resend cooldown is 60 seconds, with three sends per phone/hour. IP limits are also enforced.
- Store credentials in platform-appropriate protected storage. Do not put tokens in URLs, analytics or logs. Access lasts 15 minutes; refresh family lifetime is 30 days.
- Serialize refresh calls. A reused rotated refresh token revokes its entire family. Do not blindly replay refresh after a network timeout; a lost replacement may require signing in again.
- Logout and session revocation invalidate subsequent requests immediately. Provider OAuth and passkeys are not implemented; phone change is described below.
- Phone changes are implemented: POST /auth/phone-change/request with phoneE164/countryCode, then POST /auth/phone-change/verify with phoneE164/code. Require original family sign-in within 15 minutes; refresh does not renew proof. Challenge is purpose-bound and caller-bound, with the same durable OTP limits. Existing destination accounts return phone-unavailable after proof and are never merged. Successful verification returns sign_in_required and revokes every session, device registration and restricted privacy token. Sign in using the new number; the shared 60-second send cooldown still applies. Cross-country account migration is not supported. If the success response is lost, try signing in with the new number rather than replaying an invalid old session.
- Local development shortcut: with NODE_ENV=development and OTP_MODE=development, request a sign-in code for +919000000001, then verify with 000000. This is the only fixed pair, and it works only for normal sign-in after a fresh request. The usual ten-minute expiry, one-use rule, five-attempt limit and resend limits still apply. Privacy and phone-change challenges, and every other phone number, use random codes printed only in the local terminal. The fixed pair is unavailable in production and proves no phone ownership. Never put it in a released app.

## Module errors

Also handle the [shared error contract](COMMON.md#errors). These are module-level codes; applicability depends on the endpoint and current state. HTTP status alone is insufficient.

| HTTP | Code | Meaning | Client action |
| --- | --- | --- | --- |
| 400 | `country-change-unavailable` | Phone changes must stay in your account country. | Show a contextual error using code; correct input/state or respect the documented limit before retrying. |
| 400 | `display-name-required` | A display name is required for a new account. | Ask for name and retry verification with the same valid code. |
| 401 | `invalid-otp` | That code is invalid or expired. | Let the user correct the code or request a new one. |
| 401 | `invalid-session` | Sign in again to continue. | Coordinate refresh once if appropriate; if refresh fails, sign in again. |
| 403 | `reauthentication-required` | Sign in again before changing your phone. | Show a contextual error using code; correct input/state or respect the documented limit before retrying. |
| 404 | `not-found` | Session not found. | Refresh the list/access state; avoid exposing whether another user owns the resource. |
| 409 | `phone-unavailable` | This verified destination cannot be linked to this account. | Show a contextual error using code; correct input/state or respect the documented limit before retrying. |
| 409 | `phone-unchanged` | This phone number is already yours. | Show a contextual error using code; correct input/state or respect the documented limit before retrying. |
| 429 | `rate-limited` | Too many requests. Try again later. | Show a contextual error using code; correct input/state or respect the documented limit before retrying. |
| 503 | `auth-unavailable` | Authentication is not configured. | Show a contextual error using code; correct input/state or respect the documented limit before retrying. |

## Detailed request and response contracts

Shapes below are **type notation**, not JSON to send: `?` means optional, `|` means alternatives, and comments show constraints/defaults. Requests reject unknown write fields. JSON uses actual values. Runtime cross-field/business rules are in the client guidance above. The linked OpenAPI is the machine-readable source.

### POST /v1/auth/otp/request

Operation: `requestOtp`. Access: Public.

Request body (application/json, required):

```text
{
  phoneE164: string /* pattern="^\\+91[6-9]\\d{9}$" */
  countryCode?: "IN"
}
```

Response HTTP 202:

```text
{
  status: "accepted"
}
```

### POST /v1/auth/otp/verify

Operation: `verifyOtp`. Access: Public.

Request body (application/json, required):

```text
{
  phoneE164: string /* pattern="^\\+[1-9]\\d{6,14}$" */
```

```text

}
```
